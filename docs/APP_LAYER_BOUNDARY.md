# 「哪些函数属于应用层」——七条静态路线已排除

> **这份文档只回答一件事**：在**无符号表、无 AOT 元数据文档、不可运行**这三个条件下，
> 有没有办法把 321,244 个函数（IDA 同等口径）分成「应用层」与「运行时/编译器生成」两堆。
>
> **答案：没有已知的可行路径。** 下面七条都试过，逐条写明假设、方法、结果与在哪一轮被否证。
>
> **写给谁**：写给下一个会想到「那试试 X」的人（包括下一轮的我）。
> 请先读完这七条再动手——它们覆盖了从"按段"到"按大小"的全谱，重复其中任何一条都不会有新结果。

---

## 为什么这个问题重要

objective 的前两句是「**函数数量对等**」与「**每个函数功能相等**」。
但"函数数量"这个数本身取决于口径：

| 口径 | 数量 |
|---|---|
| IDA `af` 全镜像（无 PDB、`cc 129`、`ready=true`） | **321,244** |
| `.pdata` 的 `RUNTIME_FUNCTION`（非叶函数） | **277,094** |
| 复刻件同口径 | 186,732 |

两侧都含大量 AOT 运行时与编译器生成代码。**只要不知道「应用层」有多少个函数，
就无法说"函数数量对不对等"** —— 现在只能说"全镜像口径差 134,512，比值 0.581"。

## 七条路线

### 1. 按段划分

**假设**：应用层代码集中在某个段或某个地址区间。
**方法**：按节统计函数密度。
**结果**：`.text` 是单个 51.7 MB 的连续节，函数均匀分布，无内部分界。
**否证于**：`BLOCKERS` §47。

### 2. 抽样读 `64–256 B` 那段

**假设**：中等大小函数里"逻辑代码"与"胶水代码"可人为区分。
**方法**：随机抽 12 个反编译，人工分类。
**结果**：两侧都得到"5 运行时 / 7 逻辑"，**但分类是主观的**，无法复算。
**否证于**：`BLOCKERS` §49（记为低置信、不据此归因）。

### 3. 从入口做可达性

**假设**：应用层 = 从 `main`/`DllMain` 可达的函数。
**方法**：BFS。
**结果**：**1.5%**。失败原因不是间接调用（只占 12.6%），而是**函数指针被当作数据存储**。
**否证于**：`BLOCKERS` §50。

### 4. 把表边接进可达性

**假设**：把"指向函数的指针表"当边接进 BFS 就能大幅提高可达率。
**方法**：接 20,608 段表边。
**结果**：1.5% → **2.2%**（且这是**过近似上界**）。表不是那座桥。
**否证于**：`BLOCKERS` §51 / R618。

### 5. MethodTable 头部 + vtable 槽

**假设**：解析 AOT 的 `MethodTable`，就能得到"类型 → 方法集"，进而界定应用层。
**方法**：找到 363 个 `MethodTable`，按 dotnet/runtime 文档验证布局（`sizeof` = 0x18、槽数在 +0x10），
读出 19,630 个槽、1,743 个互异函数、344 条基类边。
**结果**：**结构全部解出且可复算**（见 `BLOCKERS` §79 / §81），但**总量只覆盖 0.63% 的函数**。
**否证于**：R644（总量减法）/ R647（修正为 0.63%）/ R648（无第二层间接）。
**注**：这条路线**交付了两样可复用的东西**——`MethodTable` 读取规则与继承图，见本文末。

### 6. `.pdata` 的 unwind info 成簇

**假设**：同一编译单元的函数 unwind info 相邻，可据此分组。
**方法**：277,094 条 `RUNTIME_FUNCTION` 的 `UnwindInfoAddress` 做空间局部性统计。
**结果**：**INTERLEAVED** —— top4 桶只覆盖 13.2%，地址相邻函数的 `|Δunwind|` 中位数 130,644 字节。
**且 277,094 个函数只有 91,940 个互异 unwind**（平均 3.01 个共用），**结构上就不可能标识分组**。
**否证于**：R645。

### 7. 函数大小二分

**假设**：编译器生成的代码（胶水、thunk）比手写代码小，大小分布应双峰。
**方法**：`size = End - Begin` 的分布 + `log2` 直方图。
**结果**：**主体是平滑单峰**（64–128 字节处最高，23.6%），唯一第二群体是 **3,639 个 1–2 字节函数（1.3%）**，
更像对齐/`int3` 填充。
**否证于**：R649。**并附带否证了我自己预注册的双峰判据**——"两侧中位数差 ≥4×"对任何长尾单峰都成立。

---

## 结论

> **在无符号、无元数据文档、不可运行的条件下，静态侧没有已知路径能把 321,244 个函数分成应用层与非应用层。**

这不是"没试够"，是七条覆盖了从结构到分布的全谱之后的结果。

## 三条解锁条件

| 条件 | 能给什么 | 代价 |
|---|---|---|
| **开 IDA 库**（原版 `.i64`，1.4 GB） | 可交互判读、可交叉引用、可用 IDA 的函数类型分析 | 需 **≥3 GB 空闲内存**；本 session 因只剩 1.7–2.4 GB 而未开 |
| **原版登录凭据** | 运行期对照：断点、调用栈、模块内函数集 | 需 A 类前置（可重定向的数据根） |
| **AOT 元数据格式资料** | **已用过** —— 给出了 `MethodTable` 布局，但**给不出"应用层"的划分**（那只存在于编译期的模块信息里，AOT 不保留） | 免费，但已证明不足 |

**注意第三行**：格式资料是唯一"免费"的条件，而它已经用掉了、且**不足以回答这个特定问题**。
所以剩下的两条都要外部条件。

## 已经拿到的、与这个问题无关但可用的东西

不要把上面七条的否证误读成"什么都没得到"。它们交付了：

```
MethodTable 读取规则（已用文档验证，见 BLOCKERS §79 / §81）
  +0x00 uint   _uFlags     低 16 = 组件大小（普通类为 0）
  +0x04 uint   _uBaseSize
  +0x08 ptr    _pBaseType  指向另一个 MethodTable
  +0x10 ushort _usNumVtableSlots    ← 槽数，以此为准
  +0x12 ushort _usNumInterfaces
  +0x14 uint   _uHashCode
  +0x18 N 个 8 字节槽（N = _usNumVtableSlots；98.6% 函数入口、1.4% null）

继承图：363 个 MethodTable、344 条基类边、19 个连通分量（三组占 91.7%）
覆盖量：19,630 槽 → 1,743 个互异函数 = 0.63% of 277,094
```

**这些能回答「类型是怎么组织的」，不能回答「函数是怎么划分的」。**
