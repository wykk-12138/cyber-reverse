# 08 · `x-kpsdk-cd` 是怎么算的：本地有一套，不是转发

> 直接回答：**是本地算的**，而且**不是"加密算法"那么简单** —— 从原版的成员表看，cd 是
> **一次自证的挑战应答**：SHA-256 哈希 + 难度值 + 偏移/随机加减 + 指纹投影 + 时序，最后拼成那个头。
>
> 但要说清一个区别：`x-kpsdk-cd` 这个头**有时也用来承载加密后的 body**。两件事在同一个字段名下，容易混。

---

## 1. 决定性证据：一个类型的完整成员表（[Obs]）

在 `0x034478b1`–`0x03448000` 这一片（同一个类型的方法/属性名连续排列）里，能读出这个 solver 的全部要素：

```
状态与上下文
  get_Script / set_Script              ← ips.js 正文
  get_BasePath / set_BasePath
  get_KasadaCt / set_KasadaCt          ← 由它派生
  get_CookieName / set_CookieName
  get_IpsUrl / set_IpsUrl
  get_Bmsz / set_Bmsz                  ← Akamai 混入，见 07

挑战应答的量
  get_Answers / set_Answers            ← 应答数组
  set_Duration                         ← 耗时
  get_WorkTime / set_WorkTime          ← 握手耗时（01 §6 的 workTime）
  get_ServerTime                       ← 服务端时间
  RemoteServerTime

cd 的生成要素
  Sha256Hex                            ← SHA-256 → hex
  HashDifficulty                       ← 难度值（PoW）
  get_Offset / set_Offset              ← 偏移
  GetOffset                            ← 同一族里另有方法形态
  RandomAddSubtract                    ← 随机加减
  GetCdHeader                          ← 最终取 cd 头

入口
  <SolveAsync>d__3                     ← 这个类型的主流程（async 状态机，序号 3）
```

全片复算（池偏移）：

```
0x03447a4a  get_Answers          0x03447a6a  set_Duration
0x03447a77  get_Offset           0x03447a8d  get_ServerTime
0x03447c03  RemoteServerTime     0x03447c28  <SolveAsync>d__3
0x03447e9a  Sha256Hex            0x03447eab  HashDifficulty
0x03447f2d  RandomAddSubtract    0x03447f40  GetOffset
0x03447f52  GetCdHeader
```

**同一片里还有一整套指纹字段与随机生成器**（说明 cd 里要带指纹，而且要**随机化**以免同一客户端特征一致）：

```
get_OuterHeight/OuterWidth   get_ResolutionHeight/ResolutionWidth
get_AvailableHeight/AvailableWidth   get_NumPlugins
get_WebGlRenderer   get_FullTimeZone   get_Vendor   get_Referer   set_Fingerprint
IsChrome   GetRandomWebGLRenderer   GenRandomSizedBrowser   GenRandomChrome   GenRandomIos
```

**读法**：`Sha256Hex` 与 `HashDifficulty` 放一起 = 有一次**按难度找解**的哈希运算；
`GetOffset` + `RandomAddSubtract` = 结果还要做位置/数值上的随机化；
`GetCdHeader` 是最后一步。这不是"把 body 用密钥加密"的形状，是**"当场证明我算过"**的形状。

## 1.5 而且**有两个 solver 类型**：一个算，一个用浏览器（[Obs]）

紧邻的前一片（池 `0x03447014`–`0x034477e5`）是**另一个类型**，成员完全是浏览器操控：

```
_browsersLock   _creating   _browser   _profile   _offscreenHost   _request   _headersTcs
<Solve>d__17    <Solve>d__2   <RunWithTimeout>d__18   <LoopTurnstile>d__20
<SetCookies>d__22   <MoveMouse>d__26   <Click>d__27
<GetScript>d__3   <GetSensor>d__4   <SubmitSensor>d__5
SetProxy   DeleteCookies   MoveMouse   LoopTurnstile   MultiPartTlds   CookieDomain
get_Healthy   get_Sensor   get_LzAlphabet   get_MobileDv   get_Payload   get_Failed
<Failed> <Payload> <Ct> <Dt> <Im> <Dv> k__BackingField      ← Kasada 的字段族
```

| 成员 | 真 VA（`str` 核实） | 说明 |
|---|---|---|
| `_offscreenHost` | `0x143448202`（另有 `OffscreenHost` `0x14343d15c`） | DotNetBrowser 的**离屏渲染**宿主 —— 无头但有完整内核 |
| `MoveMouse@` / `<MoveMouse>d__26` | `0x143448170` / `0x143447ee2` | 在真页面上做**鼠标移动** |
| `<MoveMouseAndClickAsync>d__13` / `<MoveMouseAndClickWithoutTrajectoryAsync>d__11` | `0x14348bf91` / `0x14348bf44` 同一片 | **带轨迹 / 不带轨迹**两种点击 —— 典型反检测写法 |
| `<PressMouseOnScreenAsync>d__16` / `<ReleaseMouseOnScreenAsync>d__15` / `<PressKeyAsync>d__17` / `get_SuppressInput` | 同上片（`0x14348bfc5` 起） | 按下/释放/按键/抑制输入 |
| `<LoopTurnstile>d__20` | `0x143448xxx` 片 | 循环过 **Turnstile** |
| `get_LzAlphabet` / `set_LzAlphabet` / `LzAlphabet` | `0x1434484a9` / `0x1434484b8` / `0x143448511`、`0x146dee96c` | **LZ 字母表** —— sensor 数据是 LZ 压缩的 |
| `<Ct> <Dt> <Im> <Dv>` backing field | — | 与 05 §2 的 `_kasadaCt/Dt/Im/Dv` 一一对应 |

**⇒ 结论**：cd 有**两条本地实现** —— 一条纯算（§1，`GetCdHeader` 在 `0x143448d52`），一条在真浏览器里算（本节）。
两条产出同样的字段族，所以调用方可以互换。这是"`IKasadaSolver` 是个接口"的真正含义（04 §1）。

`get_LzAlphabet` 还解释了一件小事：sensor payload 里的 `d` 值是**压缩后**的尺寸类字段，
所以复现时必须用**同一套 LZ 字母表**，否则长度对不上、站点会看出客户端不认识自己的格式。

**另外一条不该忽略的**：`MoveMouseAndClickWithoutTrajectoryAsync` 与 `MoveMouseAndClickAsync` **成对存在** ——
这说明原版把"拟人轨迹"当成**可开关的成本**：默认走轨迹，赶时间或目标不敏感时关掉。
做同类系统时这条取舍直接抄得动。

## 2. 交叉验证：cd 的 payload 与属性一一对上（[Obs]）

池里有一条真实的 sensor payload（[Obs]，池偏移 `0x07191c6c`）：

```json
{"workTime":1772713428577,"id":"1aea246e801c325a64839b2db3e4df92",
 "answers":[6,3],"duration":41.8,"d":1184,"st":1772707875172,"rst":1772707876356}
```

| payload 字段 | 对应属性 | 说明 |
|---|---|---|
| `workTime` | `WorkTime` | 客户端时钟 |
| `answers` | `Answers` | 挑战应答（这里是 `[6,3]`） |
| `duration` | `Duration` | 耗时 |
| `d` | `Offset`（[Inf]） | 最可能是偏移量（`1184`） |
| `st` / `rst` | `ServerTime` / `RemoteServerTime` | 服务端时间与取回的远端时间 |
| `id` | （无对应属性，[Unk]） | 疑似传感器实例 id |

**7 个字段里 5 个能与该类型的属性名对上** —— 这就是"这个类型就是那份 payload 的模型"的证据。
（`st`/`rst` 的展开是推的：`ServerTime` 是单数，`RemoteServerTime` 是取回来的那个。）

## 3. 两件事不要混：`cd` 既当挑战应答，也当 body 容器

| 用途 | 形状 | 谁算 |
|---|---|---|
| **挑战应答**（默认） | 上面那个 JSON：指纹 + `answers` + 时序 + 哈希难度 | **本地**（§1 那套） |
| **加密 body**（按站点/按请求） | 一把密钥把请求体加密，`cd` 变成容器 | 密钥在 `ips.js` 的上下文里派生 |

第二件事**没有证据显示原版自己实现了加密原语**：

- `AesGcm` 的命中全部在 **jose-jwt 的 JWE 算法**（`AesGcmKeyWrapManagement`）与 .NET 的对称加密枚举，没有一处与 Kasada 上下文相邻；
- `AesCbc` / `CdKey` / `EncryptBody` / `BodyCipher` 在池里 **0 命中**（池是抽样，但正向命中为主，这几个是常见词，缺得反常）。

**⇒ [Inf] 结论：body 加密这一档，原版走的是"同一份脚本上下文里让脚本自己算"**（02/03 的路线），
而不是自己写一份 AES。这也解释了为什么它必须让 `ct` 与 `cd` 来自同一份脚本运行 —— 密钥在脚本的状态里。

## 4. 算法骨架（[Inf]，由成员名反推，未反编译验证）

```
输入： ips.js 正文、页面 URL、指纹（随机生成的那套）、服务端时间
1. 从脚本里拿到挑战上下文（ct / 版本 / 时间基准）
2. 对挑战 + 指纹 + 时序做 SHA-256，按 HashDifficulty 找到一个满足条件的解   ← Sha256Hex + HashDifficulty
3. 对结果施加偏移与随机加减（避免固定输出）                              ← GetOffset + RandomAddSubtract
4. 用 Answers / Duration / WorkTime / ServerTime 组装 client data
5. 编码成请求头值                                                        ← GetCdHeader
```

**[Unk] 具体公式没有**：`HashDifficulty` 的判定式（前导零？模运算？）、`RandomAddSubtract` 的作用域、
`Offset` 的量纲，都要读 `SolveAsync` 的伪代码才能定。这三个量的名字**足以描述形状，不足以复现算法**。

## 5. 和远端通道的关系（`KasadaCdSolver`）

[Obs] `KasadaCdSolver`（VA `0x143321dfa`）与 `IKasadaSolver` / `KasadaSolveRequest` / `KasadaSolveResult` 同一命名空间，
所以它是**服务通道上的一个实现**。池里另有 JSON 字段名 `clientData` / `clientdata`（`0x06fc9974` / `0x06fca25c`）。

**[Inf] 分工**：
- **本地**（§1 那个类型）：自己算 cd —— 默认路径
- **远端**（`KasadaCdSolver`）：把 `clientData` 传出去，让别人算 —— 可选路径

两者是**同一件事的两个实现**，不是两件事。这也解释了为什么接口叫 `IKasadaSolver` 而不是 `IKasadaTokenFetcher`。

## 9. 两条链路的落地位置（本轮新增，[Obs]）

顺着九个头的**对象头**（`01-protocol.md` §3.0）查 xref，两条链路各落在一个函数上：

### 9.1 请求侧（本地算出来的值 → 写进请求头）

`sub_1408F2CD0`（`0x382` 字节，async 状态机，状态在 `a1+24`）：

```c
sub_1408BAD40(headers, &off_147188198 /* x-kpsdk-cd */, rec[16]);
sub_1408BAD40(headers, &off_1471881C8 /* x-kpsdk-ct */, rec[11]);
if (has(&off_147188288 /* x-kpsdk-h */)) { v = rec[15]; if (v) set(headers, h, v); }
if (has(&off_147188310 /* x-kpsdk-v */)) set(headers, v, sub_1408EF620(rec));
```

**读法**：`rec` 是一个**结果记录**，字段下标直接对应：

| 记录槽位 | 头 |
|---|---|
| `rec[11]` | `x-kpsdk-ct` |
| `rec[15]` | `x-kpsdk-h` |
| `rec[16]` | `x-kpsdk-cd` |
| `sub_1408EF620(rec)` | `x-kpsdk-v` |

**⇒ 这就是"cd 从哪来"的答案的一半**：它不是在这个函数里算的，是从 `rec[16]` 取的。
算的地方在**产生 rec 的那一带**（`0x1408EFxxx` 家族：`sub_1408EFAB0` / `sub_1408EFB70` / `sub_1408EF620`）。

### 9.2 响应侧（服务商返回的值 → 落进对象）

`sub_141148770`（`0x3d0` 字节）—— 与 `/payload` 请求构造 `sub_1411483E0` 相邻，是它的响应处理：
连着五次「按头名取值 → 存到 `+8/+16/+24/+32/+40`」：

```c
TryGetValues(respHeaders, &off_1471881C8 /* ct */, out v) → obj+16
TryGetValues(respHeaders, &off_1471881F8 /* dt */, out v) → obj+24
TryGetValues(respHeaders, &off_1471882B0 /* im */, out v) → obj+32
TryGetValues(respHeaders, &off_147188228 /* dv */, out v) → obj+40
```

**⇒ 走 Api 路时，cd/ct/dt/dv 全部来自服务商响应头**，客户端一个字节都不算。
这与 §9.1 的本地路形成对照：**同一个头，两条链路的来源完全不同**。
