# 08 · `x-kpsdk-cd` 是怎么算的：本地有一套，不是转发

> 直接回答：**是本地算的**，而且**不是"加密算法"那么简单** —— 从原版的成员表看，cd 是
> **一次自证的挑战应答**：SHA-256 哈希 + 难度值 + 偏移/随机加减 + 指纹投影 + 时序，最后拼成那个头。
>
> 但要说清一个区别：`x-kpsdk-cd` 这个头**有时也用来承载加密后的 body**。两件事在同一个字段名下，容易混。

---

## 1. 决定性证据：一个类型的完整成员表（[Obs]）

在 `0x034478b1`–`0x03448000` 这一片（同一个类型的方法/属性名连续排列）里，能读出这个 solver 的全部要素：

```
状态与上下文
  get_Script / set_Script              ← ips.js 正文
  get_BasePath / set_BasePath
  get_KasadaCt / set_KasadaCt          ← 由它派生
  get_CookieName / set_CookieName
  get_IpsUrl / set_IpsUrl
  get_Bmsz / set_Bmsz                  ← Akamai 混入，见 07

挑战应答的量
  get_Answers / set_Answers            ← 应答数组
  set_Duration                         ← 耗时
  get_WorkTime / set_WorkTime          ← 握手耗时（01 §6 的 workTime）
  get_ServerTime                       ← 服务端时间
  RemoteServerTime

cd 的生成要素
  Sha256Hex                            ← SHA-256 → hex
  HashDifficulty                       ← 难度值（PoW）
  get_Offset / set_Offset              ← 偏移
  GetOffset                            ← 同一族里另有方法形态
  RandomAddSubtract                    ← 随机加减
  GetCdHeader                          ← 最终取 cd 头

入口
  <SolveAsync>d__3                     ← 这个类型的主流程（async 状态机，序号 3）
```

全片复算（池偏移）：

```
0x03447a4a  get_Answers          0x03447a6a  set_Duration
0x03447a77  get_Offset           0x03447a8d  get_ServerTime
0x03447c03  RemoteServerTime     0x03447c28  <SolveAsync>d__3
0x03447e9a  Sha256Hex            0x03447eab  HashDifficulty
0x03447f2d  RandomAddSubtract    0x03447f40  GetOffset
0x03447f52  GetCdHeader
```

**同一片里还有一整套指纹字段与随机生成器**（说明 cd 里要带指纹，而且要**随机化**以免同一客户端特征一致）：

```
get_OuterHeight/OuterWidth   get_ResolutionHeight/ResolutionWidth
get_AvailableHeight/AvailableWidth   get_NumPlugins
get_WebGlRenderer   get_FullTimeZone   get_Vendor   get_Referer   set_Fingerprint
IsChrome   GetRandomWebGLRenderer   GenRandomSizedBrowser   GenRandomChrome   GenRandomIos
```

**读法**：`Sha256Hex` 与 `HashDifficulty` 放一起 = 有一次**按难度找解**的哈希运算；
`GetOffset` + `RandomAddSubtract` = 结果还要做位置/数值上的随机化；
`GetCdHeader` 是最后一步。这不是"把 body 用密钥加密"的形状，是**"当场证明我算过"**的形状。

**⇒ 结论**：cd 有**两条本地实现** —— 一条纯算（§1，`GetCdHeader` 在 `0x143448d52`），一条在真浏览器里算（本节）。
两条产出同样的字段族，所以调用方可以互换。这是"`IKasadaSolver` 是个接口"的真正含义（04 §1）。

`get_LzAlphabet` 还解释了一件小事：sensor payload 里的 `d` 值是**压缩后**的尺寸类字段，

**另外一条不该忽略的**：`MoveMouseAndClickWithoutTrajectoryAsync` 与 `MoveMouseAndClickAsync` **成对存在** ——
这说明原版把"拟人轨迹"当成**可开关的成本**：默认走轨迹，赶时间或目标不敏感时关掉。
做同类系统时这条取舍直接抄得动。

## 2. 交叉验证：cd 的 payload 与属性一一对上（[Obs]）

池里有一条真实的 sensor payload（[Obs]，池偏移 `0x07191c6c`）：

```json

 "answers":[6,3],"duration":41.8,"d":1184,"st":1772707875172,"rst":1772707876356}
```

| payload 字段 | 对应属性 | 说明 |
|---|---|---|
| `workTime` | `WorkTime` | 客户端时钟 |
| `answers` | `Answers` | 挑战应答（这里是 `[6,3]`） |

## 3. 两件事不要混：`cd` 既当挑战应答，也当 body 容器

| 用途 | 形状 | 谁算 |
|---|---|---|
| **挑战应答**（默认） | 上面那个 JSON：指纹 + `answers` + 时序 + 哈希难度 | **本地**（§1 那套） |
| **加密 body**（按站点/按请求） | 一把密钥把请求体加密，`cd` 变成容器 | 密钥在 `ips.js` 的上下文里派生 |

第二件事**没有证据显示原版自己实现了加密原语**：

- `AesGcm` 的命中全部在 **jose-jwt 的 JWE 算法**（`AesGcmKeyWrapManagement`）与 .NET 的对称加密枚举，没有一处与 Kasada 上下文相邻；
- `AesCbc` / `CdKey` / `EncryptBody` / `BodyCipher` 在池里 **0 命中**（池是抽样，但正向命中为主，这几个是常见词，缺得反常）。

**⇒ [Inf] 结论：body 加密这一档，原版走的是"同一份脚本上下文里让脚本自己算"**（02/03 的路线），
而不是自己写一份 AES。这也解释了为什么它必须让 `ct` 与 `cd` 来自同一份脚本运行 —— 密钥在脚本的状态里。

## 4. 算法骨架（[Inf]，由成员名反推，未反编译验证）

```
输入： ips.js 正文、页面 URL、指纹（随机生成的那套）、服务端时间
1. 从脚本里拿到挑战上下文（ct / 版本 / 时间基准）
2. 对挑战 + 指纹 + 时序做 SHA-256，按 HashDifficulty 找到一个满足条件的解   ← Sha256Hex + HashDifficulty
3. 对结果施加偏移与随机加减（避免固定输出）                              ← GetOffset + RandomAddSubtract
4. 用 Answers / Duration / WorkTime / ServerTime 组装 client data
5. 编码成请求头值                                                        ← GetCdHeader
```

**[Unk] 具体公式没有**：`HashDifficulty` 的判定式（前导零？模运算？）、`RandomAddSubtract` 的作用域、
`Offset` 的量纲，都要读 `SolveAsync` 的伪代码才能定。这三个量的名字**足以描述形状，不足以复现算法**。

## 5. 和远端通道的关系（`KasadaCdSolver`）

[Obs] `KasadaCdSolver`（VA `0x143321dfa`）与 `IKasadaSolver` / `KasadaSolveRequest` / `KasadaSolveResult` 同一命名空间，
所以它是**服务通道上的一个实现**。池里另有 JSON 字段名 `clientData` / `clientdata`（`0x06fc9974` / `0x06fca25c`）。

**[Inf] 分工**：
- **本地**（§1 那个类型）：自己算 cd —— 默认路径
- **远端**（`KasadaCdSolver`）：把 `clientData` 传出去，让别人算 —— 可选路径

两者是**同一件事的两个实现**，不是两件事。这也解释了为什么接口叫 `IKasadaSolver` 而不是 `IKasadaTokenFetcher`。

## 9. 两条链路的落地位置（[Obs]）

### 9.1 请求侧（本地算出来的值 → 写进请求头）

`sub_1408F2CD0`（`0x382` 字节，async 状态机，状态在 `a1+24`）：

```c
sub_1408BAD40(headers, &off_147188198 /* x-kpsdk-cd */, rec[16]);
sub_1408BAD40(headers, &off_1471881C8 /* x-kpsdk-ct */, rec[11]);
if (has(&off_147188288 /* x-kpsdk-h */)) { v = rec[15]; if (v) set(headers, h, v); }
if (has(&off_147188310 /* x-kpsdk-v */)) set(headers, v, sub_1408EF620(rec));
```

**读法**：`rec` 是一个**结果记录**，字段下标直接对应：

| 记录槽位 | 头 |
|---|---|
| `rec[11]` | `x-kpsdk-ct` |
| `rec[15]` | `x-kpsdk-h` |
| `rec[16]` | `x-kpsdk-cd` |
| `sub_1408EF620(rec)` | `x-kpsdk-v` |

**⇒ 这就是"cd 从哪来"的答案的一半**：它不是在这个函数里算的，是从 `rec[16]` 取的。
算的地方在**产生 rec 的那一带**（`0x1408EFxxx` 家族：`sub_1408EFAB0` / `sub_1408EFB70` / `sub_1408EF620`）。

### 9.2 响应侧（服务商返回的值 → 落进对象）

`sub_141148770`（`0x3d0` 字节）—— 与 `/payload` 请求构造 `sub_1411483E0` 相邻，是它的响应处理：
连着五次「按头名取值 → 存到 `+8/+16/+24/+32/+40`」：

```c
TryGetValues(respHeaders, &off_1471881C8 /* ct */, out v) → obj+16
TryGetValues(respHeaders, &off_1471881F8 /* dt */, out v) → obj+24
TryGetValues(respHeaders, &off_1471882B0 /* im */, out v) → obj+32
TryGetValues(respHeaders, &off_147188228 /* dv */, out v) → obj+40
```

**⇒ 走 Api 路时，cd/ct/dt/dv 全部来自服务商响应头**，客户端一个字节都不算。
这与 §9.1 的本地路形成对照：**同一个头，两条链路的来源完全不同**。

## 10. 槽位全表 + 一个必须先说的**归属疑问**（本轮修正）

### 10.1 `rec` 槽位（[Obs]，`sub_1408F2CD0` 全文 + 三处交叉）

| 槽位 | 内容 | 证据 |
|---|---|---|
| `rec[4]` / `rec[5]` | **前置校验用**（`sub_141CF4290(_, rec[4])` / `sub_142E7BF00(&off_144981808, rec[5]+16, …)`） | `0x1408f2ef7` / `0x1408f2ef7` 起 |
| `rec[9]` | `x-kpsdk-dt` | `sub_1408EFC50` `0x1408efd1e` |
| `rec[10]` | `x-kpsdk-im` | `sub_1408EFC50` `0x1408efd56` |
| `rec[11]` | `x-kpsdk-ct` —— **缺它就异步跑 `EFAB0`** | `sub_1408F2CD0` `0x1408f2f2e` |
| `rec[13]` | **第二必需量** —— 缺它就异步跑 `EFB70`（`EFB70` 无参，只读 `rec`） | `sub_1408F2CD0` `0x1408f2f35` |
| `rec[15]` | `x-kpsdk-h` | `sub_1408F2CD0` `0x1408f2de0` |
| `rec[16]` | **`x-kpsdk-cd`** | `sub_1408F2CD0` `0x1408f2d9d` |
| `rec[17]` | **`accept-language` 的值**（不是 body —— 本轮修正） | `sub_1408EFC50` `0x1408efe98` + `names_at 0x146F6C498` |
| `rec[7]` / `[14]` | 未定（只出现在 `Reset` 的清零里） | `sub_1408EF930` |

**`rec[11]` 与 `rec[13]` 是两个并列的"必需量"**，各自缺了就各自触发一次异步生产：

```c
if (check('Kasada'))                       // 0x146DDA8A8 = 'Kasada'
{
    if (!rec[11]) { await sub_1408EFAB0(rec, 0, 0, 0, 1); }   // 生产 ct
    if (!rec[13]) { await sub_1408EFB70(rec); }               // 生产第二必需量（无参）
    setHeader(cd ← rec[16]);  setHeader(ct ← rec[11]);
    if (hasHeader(h) && rec[15]) setHeader(h ← rec[15]);
    if (hasHeader(v) && sub_1408EF620(rec)) setHeader(v ← sub_1408EF620(rec));
}
```

**⇒ 两个异步生产器形状不同**：`EFAB0` 带四个参数（含一个 `1`），`EFB70` 只带 `rec`。
所以 `rec[13]` 是**能只从 `rec` 已有状态推出来的量**，而 `rec[11]`（ct）需要外部输入。
**[Unk]** `rec[13]` 到底是什么 —— 但它的取值范围已经收窄成"`rec` 的纯函数"，这比上一轮具体多了。

`sub_1408EFC50` 是**上游请求构造器**：把 `ct/dt/im/v` + `user-agent` 装进请求头，注册 200 处理器。
**它不是算 cd 的地方**，而是拿 `rec` 里已有值去发请求。

### 10.2 一条负结论：**没找到写 `rec[16]` 的代码**

已反编译的 Kasada 家族函数里，`rec[16]`（cd）**只被读、只被 Reset 清零，没有写入点**。
这是一个需要在更大范围复核的负结论（按项目规矩，负结论必须配对照），但它把可能性收窄成两条：

- **A**：cd 由异步计算的结果回填（`sub_1408EFAB0` 启动的那条 async 链还没走完）；
- **B**：本地路上 cd 根本不由客户端算 —— 它来自服务的响应（08 §9.2 已证响应侧会读 cd）。

### 10.3 归属判定完成：`Sha256Hex` 那一批归 **Akamai**，不是 cd

上一轮存疑，本轮定案。三条独立证据：

**① 同类型里有 `Bmsz`** —— `get_Bmsz` `0x1434486fb` 就在 `get_KasadaCt` 的下一格。`bm_sz` 是 Akamai 的 cookie。

**② Akamai 有独立的 `IAkamaiGenerator` 接口与两个实现**：

```
0x14331c41a   I AkamaiGenerator        ← 接口
0x143235e09   (AkamaiGeneratorHyped
0x1432364c3   &AkamaiGeneratorJevi
0x143321d3a   JeviSolver               ← 实为 Akamai 的 solver（不是第二个 Kasada 服务商）
```

**③ Akamai 的文案族与 Kasada 同规模**（11 条 vs 12 条），说明它是同一层的对手，各有各的生成器：

```
Akamai            AkamaiPixel        AkamaiGHost        AkamaiQueueName    AkamaiReferer
GetAkamaiCookie   AkamaiHandler      AkamaiQueueHandler SkipAkamai
Akamai API down (Contact Staff)      Akamai API down (Contact staff)   ← 两种大小写都在
Akamai Blocked (IP)   Akamai Challenge block   Akamai Failed   Akamai Failed (Rotating)
Akamai block          Akamai block (Rotating...)   Akamai disabled
Solving Akamai (  ·  (SBSD)  ·  (SDS)
_akamai_pid   _homeAkamai   accountAkamai   AkamaiUserAgents   AkamaiMobileUserAgents
akamai   akamaiRequest   akamaiMulticurrency
```

**④ 一个对称性佐证**：`kasadaRequest`（`0x1470ae4ec`）与 `akamaiRequest`（`0x146f7071c`）是**成对**的字段名 ——
同一层的"请求对象"，两家各一个。

**⇒ 定案**：

| 原语 | 归属 |
|---|---|
| `Sha256Hex` / `HashDifficulty` / `RandomAddSubtract` / `GetOffset`（PoW 形状） | **Akamai**（sensor 的 PoW） |
| `get_OuterHeight` / `WebGlRenderer` / `Vendor` / `Referer` / `GenRandomChrome` / `GenRandomIos` | **两者共用**（浏览器指纹池） |
| `KasadaCt` / `IpsUrl` / `CookieName` / `BasePath` / `Script` / `GetCdHeader` | **Kasada** |

**所以 §4 的"算法骨架"作废**（它建立在把 Akamai 的 PoW 当成 cd 算法的前提上）。
**Kasada 的 cd 现在只有两个确定来源**：① 脚本在本地跑出来的（§9.1，`rec[16]`）；② 服务商响应（§9.2）。
「本地自己写一份 cd 算法」这件事，**没有证据支持** —— 这和 §3 的判断一致，而且现在更硬了。

### 10.4 顺带纠正一个可能的误读：`Jevi` 不是第二家 Kasada 服务商

看到 `JeviSolver` 时第一反应是"又一家 solver 服务"。**不是。** `AkamaiGeneratorJevi` 这个兄弟名字
把归属钉在 Akamai 上。Kasada 的第三方解法只有 **HyperSolutions** 一家（04 §2.5），
另有本地 Jint / 本地浏览器两条自算路。

**这条教训值得记**：`XxxSolver` 命名在镜像里是**通用词**，不能只看后缀判归属 ——
要找它的兄弟类型（`AkamaiGeneratorJevi` 之于 `JeviSolver`），就像 `Bmsz` 之于 `Sha256Hex`。

## 11. 统一结论：**客户端不算，只搬运**（本轮汇总，[Obs]）

把九个头在本地的**每一个写入点**摊开看，它们无一例外是「从 HTTP 响应头取出来，存进记录」：

| 头 | 写入点 | 值的来源 |
|---|---|---|
| `x-kpsdk-ct` | `sub_1408F0450` +88 · `sub_1408F3AF0` +88 · `sub_1408F2CD0` | 响应头 |
| `x-kpsdk-st` | `sub_1408F0450` +104 · `sub_1408F3AF0` +104 | 响应头 |
| `x-kpsdk-fc` | `sub_1408F05E0` +112 | 响应头 |
| `x-kpsdk-h` | `sub_1408F05E0` +120 · `sub_1408F2CD0` rec[15] | 响应头 |
| `x-kpsdk-dt` | `sub_1408EFC50` rec[9] | 响应头 |
| `x-kpsdk-im` | `sub_1408EFC50` rec[10] | 响应头 |
| `x-kpsdk-cd` | `sub_1408F2CD0` rec[16] | **没有写入点**（§10.2 负结论） |
| `x-kpsdk-v` | `sub_1408EF620`（虚调用，`this+176` 或 `this+144`） | 版本 provider |
| `x-kpsdk-dv` | `sub_141148770` +40 | 服务商响应头 |

**⇒ 这不是巧合。** 整套代码的形状是：

```
谁算的             → 客户端怎么拿到          → 客户端做什么
─────────────────────────────────────────────────────────
本地脚本（Jint）   → 网络上的响应头          → 搬进 rec → 装进下一次请求
本地浏览器         → Network.requestWillBeSent → 同上
HyperSolutions     → 服务商响应头            → 同上
```

**客户端自己**从来不实现 Kasada 的算法。这解释了本项目最早就想不通的三件事：

1. **为什么"体感跟自主生成一样"** —— 因为它确实不是调用外部服务（本地路），但也不是自己算；
2. **为什么 100 个任务占用不高** —— 因为客户端只是 JS 解释器 / 一个池化浏览器（`_browserSemaphore`）+
   一堆字段搬运，没有每个任务一套重型进程；
3. **为什么 `Reset` 要一次清六个槽位**（02 §1.5.1）—— 因为那六个是"这一次握手的全部结果"，
   半份结果比没有更糟（拿旧 ct 配新 st 就是一次不可能的组合）。

**⇒ 对"cd 怎么算"的最终回答**：
**客户端没有 cd 算法，也不需要。** cd 的算法在 `ips.js` 里（本地跑脚本时由脚本产出），
或在服务商那侧（走 Api 时由服务商产出）。客户端负责的是**搬运与一致性** ——
这正是 §9.1 那个设头函数的全部工作，也是 §10.2 找不到写入点的原因。
