# 每项度量声称什么、证据到哪一级、哪个方向会漏

> 本文**不出现具体数字**（数字只有一个来源：`docs/METRICS.md`，由 `python tools/metrics_report.py` 生成）。
> 这里只回答三件事：**这个数在说什么**、**它是 Observation 还是 Inference**、**它往哪个方向会错**。

写这份表的直接原因：同一个 session 里我修正过四次自己的度量，四次都是同一件事 ——
**把一个间接信号当成了事实**。R585→R587（共享数据根归因）、R598（导入 API ≠ 应用使用）、
R602（字面量当事实源）、R603（读取候选当写入目标）。

**每一次都让数字看起来更糟，所以不像偷懒，更像认真。** 这种错只能靠逐项写清边界来防。

---

## 一、名字级绑定缺口（`tools/bind_diff.py --buckets`）

| 项 | 内容 |
|---|---|
| **声称** | 原版编译后的 XAML 绑定了某个成员名，而复刻件源码里**这个字节序列一次都没出现** |
| **证据等级** | 名字是否出现：**Observation**（扫源码）。"这是一个缺口"：**Inference** |
| **会漏的方向** | **少报**。整源搜索只要名字在别处出现过就算"有" —— `Models.Notification.Timestamp` 就是因为 `RunHistory.Timestamp` 存在而被判"有"，而它其实是真缺（R583） |
| **不会错的方向** | 报出来的那些，名字确实没出现过 |
| **已知的具体漏检** | `Notification.Timestamp`（已单列，R583/R584 有界论证：真值至少比报的多一条） |
| **同族工具** | `--per-file` 更严格，但对**定位不到类体**的类型静默跳过（R583 实测：契约类型里有一部分它看不见） |

## 二、类型级绑定缺口（`tools/bind_scope.py`）

| 项 | 内容 |
|---|---|
| **声称** | 对复刻件声明了的每个类型，契约绑在它上面的每个成员名都出现在**该类体 + 其祖先**里 |
| **证据等级** | **Observation**，且有**独立实现交叉验证**（R585：另写一份不复用其代码的检查，在两者共同覆盖的类型集上结论一致） |
| **会漏的方向** | **少报**。`DECL` 认不出**位置记录**与**枚举**，这类类型被 `continue` 跳过，而"缺口"计数不会因此变化（R580）。R580 加了 `types examined` 计数才让这个方向可见 |
| **交叉验证的边界** | 只在**两者都能定位**的类型上一致；独立实现多覆盖的几个里挖出两条，均已在别处记过 |
| **不会错的方向** | 报出缺口的类型，成员名确实不在类体与祖先里 |

## 三、类型缺失（`tools/bind_diff.py --type-presence`）

| 项 | 内容 |
|---|---|
| **声称** | 契约里的某个类型名，在源码里**找不到同名声明** |
| **证据等级** | 名字测试：**Observation**。"这个类型缺失"：**Inference** |
| **会错的方向** | **多报与少报都有**：<br>• 多报：简单名匹配把**同名不同物**算成"存在"。已证一例 `Cybersole.Models.State` —— 复刻件的 `State` 是 `Cybersole.Stores.Scripts` 里一个不相干的枚举（R581）<br>• 少报：`Cybersole.Models.X` 在复刻件里写作 `Cybersole.Core.Models.X` 时被算"存在"，而那**是对的**（AGENTS §0 允许改名） |
| **为什么不改成严格命名空间** | 已实测（R581 的历史测量，非当前度量值）：要求命名空间一致会让数字涨到原来的数倍，其中**大多数**是"同一类型摆放不同"的误伤。**证据不足以区分"搬家"与"同名不同物"，所以规则保持宽松** |
| **不会错的方向** | 判为"存在"且成员覆盖率满分的那一批，确实是同一类型（R582 抽查可疑项，绝大多数成员全在） |
| **那批 ABSENT 逐条分类了吗** | **是**（R619/R620）→ `docs/TYPE_PRESENCE_TRIAGE.md`，由 `analysis/type_presence_triage.py` 生成。分类用**统一的判别力阈值**：成员总数 < 3 的契约一律 `UNKNOWN`（一个成员分不清"没实现"与"改名且成员名也改了"）；满覆盖 → `RENAMED`（映射已记）；≥50% 且命中 ≥2 → `PARTIAL`；其余 → `UNIMPLEMENTED` |
| **这份分类会漂吗** | 有守卫：`TypePresenceTriageTests` 要求**分类行数 = 本度量的 ABSENT 数**，两侧工具互相校验，不硬编码任何数字 |

## 四、成员形状差异（`tools/shape_audit.py`）

| 项 | 内容 |
|---|---|
| **声称** | 契约把某成员当**属性**绑定，而复刻件里它要么不存在、要么是方法、要么只有 getter |
| **证据等级** | **Observation**（类体文本的形态） |
| **会漏的方向** | 曾经**误归类**：返回类型字符类缺 `?`，把"有但形状不同"报成"不存在"（R575 修）。**总数不变**，因为两种都是不匹配 |
| **逐条处置** | `docs/SHAPE_GAPS.md`（R575）：需要选择模型 / Unknown（同名撞名，判据无判别力）/ 结构差异 / prop-get / 可能改名 / 真缺 |
| **"需要选择模型"那一类已经量到底了吗** | **是**（R578 + R607）。两次调查：① 该类有没有**同名**无参方法 → 没有；② 有没有**别的**无参方法 → 有，但与目标动作无等价证据；③ 那批"该类一个无参方法都没有"的成员，**父类**有没有可继承的 → 基类全在复刻件源码之外（Avalonia 的 `UserControl` / `Window`），因此是 **Unknown 而不是"没有"**。三类合计**可做数为零** |
| **为什么不用继承来的方法** | `Window.Close()` 这类确实存在，但把某个 `RemoveStore` / `Delete` 映到 `Close()` 是**猜语义**，与"拒绝给 `Timestamp` 塞 `DateTime.Now`"同一条纪律 |
| **不会错的方向** | 报出来的每一行，形态确实与"可绑定属性"不符 |

## 五、文案缺口（`tools/copy_audit_report.py`）

| 项 | 内容 |
|---|---|
| **声称** | locale 表里某个键，**它的值**和**它的 key 名**在源码里都一处没有 → 代码从不查这条文案 |
| **证据等级** | **Observation**（修好转义比较之后，R589/R590）；"不查" 的判据在 R622 改过：key 名出现即算在用 |
| **会漏的方向** | **少报**：值若是**运行时拼接**出来的，整串不出现也能被判"缺失" —— 反过来，若在别处以别的形式出现，会被算"有" |
| **R622/R626 改了什么** | 旧判据只查"**值**是否连续出现在源码里"。两处不成立：① 走 locale 的应用**不把值写进源码**，它按 key 查表；② 含换行的值常被写成**两个相邻字面量**，整串永不连续。现在的判据是：**值（或它的每一段）出现在源码里，或 key 名出现在注释之外的代码里** |
| **为什么 key 必须在注释之外** | R623 第一版用 `key in text`，于是 `// Utilities.StoreGroups.Delete.UsedMessageFormat` 这种**注释**也算"被引用"——数字恰好对了，规则是错的。R626 剥掉注释后再判 |
| **剩下三条是什么** | 不是"文案不可得"，而是**缺代码路径**：`Data.Restore.Confirm.Message`（恢复流程存在、缺**确认**这一步）、`ProfileCsv.Error.UnknownCountry` / `UnknownState`（校验器 6 条分支实现了 4 条） |
| **不会错的方向** | 报出来的那几条，明细表逐条列了键与完整原文（`docs/COPY_QUEUE.md`），可以人工核对 |
| **这份表会漂吗** | 有守卫：`CopyAuditConsistencyTests` 要求**明细行数 = 汇总的 missing 数**（R590 就是这两个消费者用了不同判据） |
| **已修的两个假阳性** | `Utilities.StoreGroups.Delete.MessageFormat`、`Settings.General.MonitorConcurrency.Tooltip` —— 值里含 `"{0}"` / `"Shared Monitor"`，源码写作转义形式，旧判据匹配不上（R589） |

## 六、数据文件名对照（`tools/datafiles_diff.py`）

| 项 | 内容 |
|---|---|
| **声称** | ① 原版**数据目录**里的每个 `.json`，复刻件源码里都提到了；② 复刻件提到的名字里，有哪几个在数据目录与镜像字面量中都查不到 |
| **证据等级** | ①：**Observation**，但**只覆盖这台机器、这个账号、当前状态**（只读列举 `%APPDATA%\Cybersole`）<br>②：**Observation** |
| **会漏的方向** | • 原版只在**尚未达到的状态**下才写的文件，目录里没有 → 会被当成"不存在"<br>• "**提到了**" ≠ "**写了**"：`license.json` 就是读取候选而非写入目标（R603）<br>• 镜像字面量会**漏掉运行时拼接的名字**（`checkoutHistory.json` 真实存在却不作为整串出现），也会**拣到不是文件的名字**（`public.json` 是 Apple UTI、`products.json` 是 URL 路径） |
| **不会错的方向** | 数据目录里确实存在的文件，是"原版写过这个文件"的直接证据 |
| **为什么把目录当事实源** | R600 一开始只用字面量，于是把 `checkoutHistory.json` 误报成"仅复刻件有"（R602 更正） |

| 项 | 内容 |
|---|---|
| **声称** | 按"类存在但缺成员"与"类型整体不存在"两桶分开的缺口数 |
| **证据等级** | 同第一、第三项，是它们的另一种切法 |
| **会错的方向** | 同第一、第三项 |

## 八、原版绑定描述符表（`tools/descriptor_report.py`）

| 项 | 内容 |
|---|---|
| **声称** | 原版镜像里的绑定描述符条目/类型数，以及它们与 XAML 绑定表的差集 |
| **证据等级** | **Observation**（读 TSV，TSV 由 `analysis/binding_descriptors.py` 在 IDA 里导出） |
| **会漏的方向** | TSV 是**派生件**；IDA 没解析到的描述符不会出现在里面。差集里"只在描述符表"那一侧**不等于**"XAML 没用它" |

---

## 九、一句话

> 八项度量里，**没有一项能单独证明"两侧行为相同"**。它们能证明的是：
> 某个名字/类型/形态/文案/文件名在**某一侧存在或不存在**。

> **度量的价值不在于数字大小，而在于"这个数往哪个方向会错"写得够不够清楚。
> 写清楚了，一个偏小的数仍然可信；写不清楚，一个零也可能只是没检查。**
