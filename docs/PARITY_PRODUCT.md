## 4. 函数 / 字符串数量（同口径：IDA）

两个产物都用 IDA 自动分析 + PDB 符号加载，同一套 `idautils` 口径：

| 指标 | 原版 5.18.32 | 复刻件 AOT | 差 |
|---|---|---|---|
| **函数总数**（`idautils.Functions()`） | **321,244** | **187,328** | −133,916 (−41.7%) |
| 其中带名字 | 10,041（多为 CRT/编译器符号，见下） | 175,104（PDB 恢复） | — |
| 其中 `sub_*` 未命名 | 311,203 | 12,224 | — |
| **字符串数**（`idautils.Strings()`） | **324,901** | 278,728 | −46,173 (−14.2%) |
| `.pdata`/12（RUNTIME_FUNCTION 条目） | 277,094 | 170,137 | −106,957 (−38.6%) |

复算命令（一条命令同时导两侧，见 §8）：

```
python analysis\func_compare.py
```

> **踩过的坑（R433）**：第一次取复刻件函数数得 136,798，重取得 187,328。
> 原因是 **IDA 插件端口 open ≠ 自动分析完成** —— 端口在 PDB 加载阶段就监听了，函数还在持续识别。
> 判据是**窗口标题不再带 `Loading`** 且**连续两次取值相同**（187,328 两次一致）。
> 原版 321,244 两次一致，因为那个库早已分析完。

**原版并非"只有 `sub_*`"**：它有 10,041 个已命名函数，来自 CRT / 编译器 / 静态库符号
（`__CxxQueryExceptionSize`、`__stdio_common_vsprintf` 之类）。此前文档里"库里只有 sub_*"的说法**不准确**，
本条订正。

**按命名空间分解（R443，`python analysis/function_breakdown.py`）**：

| 分组 | 原版 | 复刻件 |
|---|---|---|
| `Cybersole_*`（**复刻件自己的业务代码**） | 0（无符号，测不出） | **2,485** 个函数 / **924,006** 字节 |
| `Avalonia_*`（UI 框架） | 0（原版用 WPF） | 30,414 |
| `S_P_CoreLib_*` + `System_*`（BCL） | 0（无符号） | 88,064（46,618 + 42,446） |
| `Jint_*`（JS 引擎）、`BouncyCastle_*`、`Newtonsoft_*`、`Acornima_*`、`SkiaSharp_*` 等第三方 | 0（无符号） | 约 19,000 |
| `<other named>` / `sub_*` | 10,041（CRT/编译器符号） | 12,224 + 其余 |

**这条分解改变了"差 41.7%"怎么读**：

1. **业务代码在产物里的可见规模是 2,485 个函数 / 0.92 MB**（占 187,328 的 1.3%）。其余 98.7% 是 BCL、
   UI 框架、JS 引擎、加密库、序列化器 —— 这些**不是"我们写的"**。
2. 复刻件总代码字节约 25.9 MB ↔ 原版 `.text` 51.7 MB，比例约 **0.50**；函数数比例 **0.58**。
   两个比例同量级，说明差异是**系统性的（框架规模）**，不是某一层整体缺失。
3. 原版侧**没有对应分解**：311,203 个函数是 `sub_*`，10,041 个有名字的是 CRT/编译器符号。
   所以"原版业务代码有多少个函数"**测不出来** —— 这是 Inference 的边界，不许越过去。

**Inference（中置信）**：若原版业务代码量级与复刻件相当（约 2,500），则 321,244 里约有 318,700 属于
框架/CRT，而复刻件对应约 184,800 —— 差的 13 万余个**几乎全部落在框架层**。
**备择解释**：原版可能把更多逻辑内联进少数大函数（`.text` 平均函数大小与复刻件不同），
那样"业务函数数"会低估；用字节比例（0.50）与函数数比例（0.58）的接近程度无法排除这一解释。



**零直接 xref 的函数比例（R458，`py_eval` + `idautils.XrefsTo(ea, 0)`）**：

| | 总函数 | 零直接 xref | 比例 |
|---|---|---|---|
| 原版 | 321,244 | 3,603 | **1.1%** |
| 复刻件 | 187,328 | 6,669 | **3.6%** |

**Observation**：复刻件里"没有任何直接调用点"的函数比例是原版的 **3.3 倍**。

**Inference（低–中置信）**：主因是**间接分派面更大** —— Avalonia 的绑定/事件、`RelayCommand`、
虚方法与委托都只产生间接引用（没有 `XrefsTo`）。**备择解释**：其中一部分是死代码（见下）。

**不能这样读**：零直接 xref ≠ 死代码。`src/` 侧零引用的**类型**只有 27 个（`DEVIATIONS.md` §十），
远小于 6,669 个函数，所以"大量函数无人调用"这个说法**不成立**；这条数据只说明
**两边的分派方式不同**，不说明复刻件有更多没用的代码。



**locale 文案在产物里的存活率（R461）**：复刻件 `en.json` 的 **1142 个键全部出现在 AOT 产物字节里（100%）**
—— 逐键 `k.encode() in raw` 比对，零缺失。这说明"源码里有文案"和"产物里能取到文案"是两件事，
而后者第一次被验证。

```
python -c "raw=open(r'...\.publish-aot\Cybersole.Ui.exe','rb').read(); ..."   # 逐键 in raw
→ en.json keys: 1142 | present in artifact: 1142 (100.0%)
```

**内嵌资源在产物里的存活率（R462）**：复刻件声明 **19 个 `EmbeddedResource`**（4 个 locale JSON、
14 个引擎 HTML/JS——含 329 KB 的 `castle.js` 与 606 KB 的 `hcaptcha-spoof.js`、1 个 Brotli 字典 122 KB），
逐个比对**逻辑名**与**内容前 32 字节指纹**：

```
logical names present: 19/19 | content fingerprints present: 19/19
```

**19/19 双绿** —— AOT 既保留了资源名，也保留了内容。这是判据 c 在产物层最后一块没验过的地方。

**这些差值能说明什么、不能说明什么（必须分开写）**：

- **Observation**：函数数、字符串数、`.pdata` 条目数在原版与复刻件之间差 38%–57%。
- **不能**据此说"复刻件缺 57% 的功能"。原版是 **WPF** 应用（12 个资源含 9 个图标、`PresentationFramework`
  系调用），复刻件是 **Avalonia**；两者的 UI 框架、序列化器、HTTP 栈、压缩实现各自带来成千上万个
  模板实例化函数。原版还有 39 个 Brotli 导出所对应的静态库副本。
- **Inference（置信度低）**：真正可比的是"业务函数"数量，而"业务函数"的边界需要函数级语义对应才能划定——
  这正是 §5 没能做的那一步。
- 因此本条整体判 **Unknown**，缺的证据写在 §6。

## 5. rea `compare_functions` / `compare_artifacts` 为什么没跑成

实测（`mcp__rea__binary_session`，rea 6.9.0，255 工具在线）：

| provider | 状态 | 原因 |
|---|---|---|
| ghidra | unavailable | `Set GHIDRA_INSTALL_DIR …`（未装） |
| hopper | unavailable | `not supported on win32` |
| **ida** | unavailable | `Set REA_IDA_MCP_CONFIG to an upstream IDA MCP JSON registration` |
| kuna | unavailable | `Set REA_KUNA_COMMAND …`（未装） |
| rea-dotnet-static | **available** | 只对**有 CLR 元数据**的产物有效 → 对 NativeAOT 原版无效 |
| rea-artifact-graph | **available** | `inspect_artifact` **takes no path**，须先 `open_binary`，而 PE 的 `open_binary` 要 native provider |

**不是没配好，是版本契约对不上**：REA 的 `ida` attached profile 只接受 **legacy 工具名**
（`get_metadata` / `list_functions` / `decompile_function`，upstream 1.4.0）。本机 `ida_pro_mcp`
插件是新版目录（`list_funcs` / `decompile` / `server_health`，66 工具，`analysis\ida.py tools` 实测）。

- **降级插件可以通这条路，但代价是拆掉 400 多轮依赖的 66 工具矩阵** —— 不做。
- **装 Ghidra 也可以**（`GHIDRA_INSTALL_DIR`），但 Ghidra 分析 123 MB NativeAOT 的时间与内存代价
  远高于 IDA，且会引入第三套反编译口径 —— 留作备选，未做。

**替代证据**（本轮采用）：IDA 直连两边取同口径计数（§4）+ `pe_triage`/`pe_diff` 取 PE 层事实（§2/§3）。
这满足"可复算"，但**不满足"逐函数对照"**。

### 一、先试了按段分，没用

原版只有一个 `.text` 段（`321,244` 全在里面），按段分没有判别力。改用**函数大小直方图**。

### 三、差的构成

```
总差                    134,512   （比值 0.581）
其中 ≤16 B 一档贡献      48,777   （36.3%）
其中 ≤32 B 两档合计      66,687   （49.6%）
```

**近一半的差落在 ≤32 字节的函数里。**

反过来看**大于 64 字节**的部分：


**在"大于 64 字节"这一档，复刻件是原版的 69.3%；而总量比值是 58.1%。**

### 四、怎么读这个结果

**Observation**：直方图与比值如上，两侧条件全对齐。

**Inference（中）**：
- 原版 26.6% 的函数 ≤16 字节 —— 与 NativeAOT 的**泛型实例化 thunk、运行时跳板、转发桩**大量生成的形态一致；
- 复刻件同样是 NativeAOT（.NET 8），同现象存在但规模小（19.6%）；
- 所以"函数数量对等"这个总量指标**被极小函数的生成规模主导**，
  它更像"两个编译器各自展开了多少泛型/桩"，而不像"实现了多少行为"。

**备择解释**：也可能复刻件真的少实现了大批小属性/小方法。**无法用大小分布区分这两者** ——
要区分得看这些 ≤16 B 函数各自做什么（反编译若干个样本），本轮没做。

### 五、仍然 Unknown

- 那 85,362 个 ≤16 B 函数里，thunk / 桩 / 真方法各占多少：**未分类**。
- 复刻件 36,585 个 ≤16 B 函数同理：**未分类**。
- 两者平均大小接近（153.6 vs 143.8）说明整体密度相似，但**不说明逐函数等价**。

### 六、纪律提醒

**大小分布不是行为对照。** 一个 12 字节的转发函数可以与行为无关，也可以是一次关键判断。
本节只说明"差落在哪个体量上"，**不说明差在哪些行为上**。

## R615：两侧 ≤16 B 的函数**逐个看过了，都是编译器胶水**

### 一、怎么抽的

在各自库里遍历函数，筛 `size <= 16`，按位置**等距抽 12 个**，用 Hex-Rays 反编译。
两侧条件同 R613（`af 0xDFFFFFF7` / metapc / 64bit / ready / 均无 PDB / `cc` 129）。

### 二、原版 12 例（`≤16 B` 共 85,362 个）

| 形态 | 样本 |
|---|---|
| 取全局地址 | `return &unk_147536E98;`、`return &unk_147536E99;` |
| 字段 getter | `return *(double *)(a1 + 48);` |
| 转发（带偏移） | `return sub_X(a1 + 32);`、`return sub_X(a1 + 1, *a1);` |
| 转发（带常量） | `return sub_X(*(_QWORD *)(a1 + 8), 1);` |
| **显式 thunk** | `// attributes: thunk  return sub_X();`（2 例） |
| **泛型实例化 shim** | `return sub_141CFE1F0(a1, a2, sub_14103BD00);` 等（3 例，同一个 helper + 不同第三参数） |
| 转发到 `nullsub` | `j_nullsub_64_209: return nullsub_64();` |

**12 例里带分支的：0。带字符串处理的：0。调用超过一处的：0。**

### 三、复刻件 12 例（`≤16 B` 共 36,585 个）

| 形态 | 样本 |
|---|---|
| **泛型实例化 shim** | `return sub_140C61220(a1, a2, sub_140146270);` 等（2 例） |
| 显式 thunk | `// attributes: thunk`（4 例，含 `j_tan_0: return tan(X);` 这类导入跳板） |
| 转发（带偏移） | `return sub_X(a1 + 8);`（2 例）、`return sub_X(a1 + 1, *a1);` |
| 字段 getter | `return *(_QWORD *)(a1 + 24);` |
| 取全局地址 | `return &unk_1441B8E61;` |
| 跳到 noreturn | `void __noreturn sub_X() { sub_Y(); }` |

**同样是：12 例里带分支的 0，带字符串处理的 0。**

### 四、结论

**Observation**：两侧各 12 个 `≤16 B` 样本，形态属同一族（getter / 转发 / thunk / 泛型 shim / 取地址），
**没有一个含业务逻辑**。

**Inference（高）**：`≤16 B` 这一档是**编译器生成的胶水**，两侧都是。
因此该档 48,777 的数量差反映的是**胶水生成量**（原版 85,362 / 复刻件 36,585，约 2.3 倍），
**不是"少了 48,777 个行为"**。

**备择解释**：抽样 12/12 未命中业务逻辑，但样本量小；可能存在少量小函数承载真实判断（例如返回值比较）。
**这一点无法用 12 例排除**，只能说在这 12 例里没出现。

### 五、还没回答的问题

`>64 B` 那一档的 45,602 差 **是什么** —— 那才是可能承载行为的范围。
本轮的结论**只覆盖 `≤16 B`**，不要外推。

### 六、仍然 Unknown

- 两侧 `≤16 B` 里胶水/非胶水的精确比例：**未分类**（12 例抽样不足以给比例）。
- 原版胶水是复刻件 2.3 倍的原因：**未查明**（.NET 10 vs 8 的 codegen？泛型实例化规模？内嵌库差异？）。
- `>64 B` 的 45,602 差：**未取样**。

### 一、抽了哪一档

## R617：可达性判据**实测失败** —— 两侧从入口可达的函数都不足 2%

### 一、做了什么

§49 提出的机械判据：从入口沿调用图 BFS，可达的算"承载行为"。
实现：`roots = inf_get_start_ea() ∪ 全部 entry`，用 `idautils.CodeRefsFrom(item, 0)` 展开直接代码引用。

### 二、结果

| | 原版 | 复刻件 |
|---|---|---|
| 总函数 | 321,244 | 186,732 |
| **从入口可达** | **4,692（1.5%）** | **1,113（0.6%）** |
| 直接 call/jmp 占比（抽 3,000 函数） | 87.4% | 100.0% |
| 间接占比 | 12.6% | 0.0% |

### 三、为什么失败：原因和我预期的不同

我在 §49 预判"路径会被间接调用截断"。实测**间接调用只占 12.6%**，并不是主导。

**真正的原因**（Inference，中高）：AOT 托管代码的入口大量是**以数据形式注册的** ——
函数指针被存进方法表 / 类型槽 / 回调表，运行时通过表项调用。
IDA 不会把这些**数据槽**变成代码引用，所以 BFS 在表项处**无处可走**。

**12.6% 的间接边足够把图切成碎片**：直接边占 87% 不代表图连通，只代表"大多数调用指令的目标在指令里写着"。

### 四、一个必须说明的测量缺陷

复刻件的"间接占比 = 0.0%"**不可信** —— 它说明我的操作数分类器没认出复刻件的调用形式
（很可能是 `j_*` 跳板被解析成 `o_near`）。**这一项两侧不可比，不作为结论。**

### 五、结论

**可达性判据不能用。** 两侧覆盖率 1.5% / 0.6%，任何基于它的比值都不是行为的度量。
**§49 提出的那条路到此关闭，且是量过之后关闭的，不是猜的。**

### 六、这意味着什么

"函数数量对等"这条判据，到此**没有可用的机械分解手段**：

| 尝试 | 结果 |
|---|---|
| 按段分 | 不可用（单一 `.text`） |
| 按大小分 | 可用，但只说明"差在哪个体量"（R614） |
| 按抽样看形态 | `≤16 B` 可用（R615）；`64–256 B` 不可用（R616） |
| **按可达性分** | **不可用（本轮）** |

剩下的只有 B 类：**恢复符号 / 建模 AOT 元数据 blob**，把方法表还原成调用关系。
那是这个项目里唯一还没试过的、能给出"哪些函数属于应用层"的机械手段。

### 七、仍然 Unknown

- 那 4,692 / 1,113 的可达集是否真的"承载行为"：**未验证**（覆盖率太低，不能代表全体）。
- AOT 方法表在 IDA 里能否被识别成结构：**未尝试**。

## R618：函数指针表**存在且量很大**，但接进 BFS 也搭不起桥 —— 分解线定量关闭

### 一、先测"有没有那种表"

扫 4 个非可执行段，找**连续 ≥8 个 qword 全部指向函数起点**的片段：

```
连续片段（run）            20,608 段
片段内条目总数            323,152
指向的不同函数            49,337   （占 321,244 的 15.4%）
```

**Observation**：镜像里确实布满函数指针表（`.rdata` 里，例如 `0x144A79010` 起 81 连）。
所以 R617 说的"AOT 入口以数据形式注册"**成立**。

### 二、把表边接进 BFS

规则：函数体内任一 `DataRefsFrom` 落在某 run 的字节范围内 → 该 run 的全部目标视为可达。
（这是**过近似**：会引入假边，但对"覆盖率上限"这个用途是可接受的，且已标注。）

```
仅直接调用边            4,692 / 321,244   （1.5%）
加表边                  6,976 / 321,244   （2.2%）
```

**只涨了 0.7 个百分点。**

**Inference（高）**：那些表**大多落在已经可达的区域内部**，或者应用层的真正入口
根本不是从 CRT 入口沿静态引用能走到的 —— 表边并不是缺失的那座桥。

### 三、所以这条线关闭了，而且是定量关闭

"函数数量对等"这个总量，四种分解口径的结果：

| 口径 | 状态 | 证据 |
|---|---|---|
| 按段 | 不可用（单一 `.text`） | §47 |
| 按大小 | **可用**（说明差集中在 ≤32 B 与 64–256 B） | §47 |
| 按抽样形态 | `≤16 B` 可用；`64–256 B` 不可用 | §48 / §49 |
| 按入口可达（含表边） | **不可用**（2.2%） | §50 / 本节 |

**没有第五种现成口径。** 再往下只能做 B 类（建模 AOT 元数据类型/方法表），
那是把数据段解析成结构，属于工程而不是探针 —— 本轮确认它**没有便宜的先导实验可做**。

### 四、因此对"函数数量对等"的诚实表述

**可以说的**：
- 同口径总量 `321,244 ↔ 186,732`（比值 0.581），条件六项全对齐（§46）；
- 差的近一半落在 ≤32 字节的胶水函数里，抽样 24 例 0 例外（§47 / §48）；
- `>64 B` 那档比值 0.693，好于总量，但其内部构成**未归因**（§49 抽样因混合而失败）。

**不能说的**：
- 不能说"复刻件缺了 13.5 万个行为"；
- 也不能说"两侧行为等价"。

**这条判据目前的准确状态：总量已测、构成部分已知、余下部分 Unknown。**

### 五、仍然 Unknown

- `64–256 B` 档 28,568 差的归因：**Unknown**（需要 B 类）。
- 应用层的真正入口在哪：**Unknown**（2.2% 的覆盖率说明从 CRT 入口走不到）。
- 那 49,337 个"表内函数"里有多少是应用层：**Unknown**。
