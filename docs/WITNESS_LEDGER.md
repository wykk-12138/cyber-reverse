# 见证候选台账（129 个）

> 池子的来历：R720 的 239 个「引用应用 locale 键」的函数 ∩ R728 的 76,547 个「字符串签名两版一致」= **129**。
> 两条判据都不是判断，一条是"引用了只有这个应用才有的字符串"，一条是"官方两个版本之间没动它的字符串引用"。
>
> **为什么要有这张表**：R730 裁定"读伪代码，人工判断"，代价是每个候选一轮。129 个候选 = 129 轮，
> 所以每一个读过、判过的候选都必须在这里留结论，**否则下一轮会有人（包括我）重新读一遍**。
>
> 台账只记**已审**的。未出现在表里的就是还没读。

## 判据（每条候选按同一套读法）

1. 反编译，看**分支结构**（不是看它调了谁）
2. 判断它有没有**可断言输出**（文本、数值、选择）
3. 如果可断言：**输出由什么决定**？若由不透明谓词或不可解析的槽位决定 → 不合格

结论只有三种：**已实现** / **不可探（写原因）** / **待审**（不写进表）。

## 已审：10 个实现 + 3 个不可探 + 2 个合并/待读，共 15 个

剩下的 **114 个待审**。

**store-groups（R732）是 2 条文案（title + message），没有 ActionFormat** —— 所以它不是三槽位形态，R732 的实现已经完整。

**闸门已有三种**（R737）：计数 != 0 / 宿主存在 / 计算对象非 null。**同一家族里三种闸门，所以每接一屏都要读它的闸门，不能照抄。**

**家族反例（R736）**：`Accounts` 与 `Accounts.Group` 同形但**参数类型与闸门都不同** —— `Accounts()` 零计数返回 null，`AccountGroup()` 从不返回 null。**共享助手会对其中一个错。**

`DeleteConfirm` 家族还有 5 个成员（Accounts ×2 / Proxies / Profiles / Groups / store-groups）**body 未读**，形状一致但不能按通例套 —— R735 与 R731 一个不做单复数、一个有单复数规则。

排序见 `analysis/witness_ranking.tsv`（按引用的占位符文案数），**38 个候选引用了带占位符的文案，其中 35 个未读**。

## 从这 6 个里能学到的（写下来，省下一轮的时间）

**三个已实现的，形状完全一样**：

```
读若干属性/计数 → 一串比较 → 选一条（或几条）locale 文案 → 代入参数
```

**三个不可探的，也完全一样**：

```
输出不是文案选择，而是 ① 控件属性赋值（UI 接线）② 在不可解析的谓词后弹框 ③ 槽位里的 label
```

**所以筛选经验是**：候选函数引用的是**带 `{0}`/`{1}` 的文案**时，大概率可探；
引用的是**短标签**（`Disabled`、`Beta`、`Create`）时，大概率是选项列表或按钮接线。

**这不是判据，是经验** —— 判据仍然是读伪代码（R730）。但它能决定先读哪个。
