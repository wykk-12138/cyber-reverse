# 这套复刻工作的做法（R200–R263 收束）

写给"下一轮的我"。这里只留下**被验证过有效**的做法，以及**踩过的坑**各一张表。

---

## 一、三种证据，各有分工

| 证据 | 能回答什么 | 不能回答什么 |
|---|---|---|
| **反编译源码 / 字符串池**（`pe_strings.txt`、`xaml_bindings.json`） | 有什么类型、什么成员、什么文案、什么表 | 交互怎么动、布局多大 |
| **GUI 观察**（cua + 像素测量） | **怎么动**、多大、在哪、什么时候出现 | 内部命名、隐藏分支 |
| **测试与守卫** | 改完之后还对不对 | 一开始该做什么 |

**主从关系**：源码是主证据；GUI 用来**消歧**（例如 `Plus/Minus` 到底是属性还是步进器，只有界面能回答）。

---

## 二、测量纪律（数字只能有这两种身份）

1. **测过的**：必须有两个样本（窗口矩形枚举 / 两个窗口宽度下的像素测量），并写进
   `docs/GUI_GEOMETRY.md`（唯一权威表），同时由 `GeometryLedgerTests` 盯着。
2. **量不出来的**：写"量不出来"并说明为什么。已确认三类：
   - 表格**最后一列**（空表时吸收余量）；
   - 启动画面的**像素内容**（`PrintWindow` 对 Avalonia/Skia 返回空白，前台化被前台锁拒绝）；
   - **下拉框内容**（点不开；`list_windows` 始终只有主窗口，两次独立复现）。

**没有第三种身份。**"估一个看起来合理的数"是本项目最大的历史债务来源（R217 一次就发现四个窗口尺寸是估的）。

---

## 三、计数纪律

1. **口径必须写在数字旁边**：`per-file` 还是 `whole-source`（R225 用错口径，把 167 当成总账）。
2. **注释不算实现**（R249：剥掉注释后真实缺口从 28 跳到 96）。
3. **噪音按形状识别**，不按见过的例子：`^(HasMultiple|Value)_\d+$` 是泛型实例化产物。
4. **棘轮**：`BindingGapRatchetTests.MaxRealGap` 只能等于**实测值**（先测后设），
   `docs/BINDING_BACKLOG.md` 标题必须与它相同（`TheBacklogDocQuotesTheCeiling` 盯着）。
5. **改完代码不要引用改之前的数字**（R251：补了 5 个却引用旧值，得出"只掉 2"的假结论）。

---

## 四、改动纪律（每条都来自一次真实翻车）

| 坑 | 规矩 |
|---|---|
| 锚点行被写两遍（`CS0102`，R252/R255） | **用替换**：`replace(anchor, anchor + 新增)`，不在 `m.end()` 拼接 |
| 字段声明了没人赋值（R243/R244/R253，四次） | 构造时取初值；受限 setter 用**受控写入方法**；`UnassignedFieldGuardTests` 盯着 |
| 猜 API 名字（R259 一轮四次） | **动手前先读那一行**（字段/方法签名） |
| `UserControl` 当 `Window` 用（R250/R261） | 视图走 `ViewHostModal.Show(...)` |
| 命令没有数据源就实现（R254 `OpenRelease`） | 先确认数据源存在；不存在就**撤掉并写清缺什么** |
| 测试单独过、批量挂（R237/R256） | 有"读到旧值"的证据 → 加**有上限重试**，断言不改；没有证据 → **只记录，不改** |

---

## 五、推进顺序（有效的切法）

- **按"类型存不存在"分组**，而不是按"缺哪些名字"逐条推进（R248：一轮做了过去五轮的量）。
- A 类（类已在、只差成员）优先；B 类（类不存在）要么抽结构，要么**明确记为结构差异**。
- **"不可得"要单独记账**（`Attributes.Platform` 三值、`AnalyticsView.OpenRelease`），不要反复尝试。

---

## 六、"死窗口"是这套工作独有的收益

七次里五次是同一件事：**窗口写好了，只差有人 `new` 它一下**。

| 窗口 | 由谁点亮 |
|---|---|
| `StoreGroupModal` | `UtilitiesView.EditStoreGroup()` |
| `NotificationView` / `UserView` | `MainWindow.OpenNotifications()` / `OpenProfile()` |
| `SmartActionsView` / `UtilitiesView` | `MonitorWindow` 三栏外壳 |
| `HistoryWindow` / `ReleaseGuideView` | `SmartActionsView.ViewLogs()` / `ReleaseView.ShowGuide()` |

不可达 UI 类因此从 **36 → 29**。绑定表里那些 `Open*` / `Show*` / `View*` 名字，
就是"谁该打开它"的名单 —— **绑定表在这里不是清单，是接线图**。

## 七、内存纪律（用户明确要求过四次）

| 指标 | 用法 |
|---|---|
| 可用物理 < **8 GB** | **停手**：不编译、不跑全套，只做文档/脚本 |
| Commit ≥ 30 GB | 软线：可继续做小步 |
| `dotnet build-server shutdown` | 每轮编译结束都跑，实测回收 ~1.2 GB |
| `analysis/memreset.ps1` | 需要管理员；被拒就如实报告 |
| 每轮 | **一次重活**（全套测试或 mutation-check），不与 IDA/GUI 同时跑 |
| 测试后 | 检查 `chrome` 进程与 `%TEMP%\cyb-chromium-*` 残留（曾泄漏 9072 个目录 / 46.7 GB） |

## 八、两种布局、两类证据（R269–R277 的产出，别忘）

### 1. 同一个东西可能有两种存法，判据要分别写

| 布局 | 形态 | 工具 |
|---|---|---|
| **A 合并式** | 一行里塞一批 `d__N` + lambda 表 | `tools/flow_dump.py` |
| **B 分行式** | 每个 `d__N` 各占一行，地址相邻 | `tools/row_groups.py` |

**教训**：R271 我按 A 去查 John Lewis，结论"走不通"；R272 发现它用 B ——
**判"这条路不通"之前，先确认自己试的是不是全部形态。**

### 2. 一张表里可能混着两类证据

| 类 | 来源 | 能否逐条对账 |
|---|---|---|
| `literal` | 直接读自一段字面量 | 能（`structure-token-*` 15/15、12/12） |
| `endpoint` | 按端点族叙述出来的行为模型 | 不能（`StartEcomSession` vs `Start`） |

落地：`StoreFlowSteps.Flow.Source`（默认 `Endpoint`）+ `StoreFlowSourceTests`。
**默认选更弱的一类，漏标只会低估。**

### 3. 子集家族会让"同时命中"看起来像矛盾

`0x03388fd2` 同时命中 `structure-token-multi`（8/15）与 `-single`（7/12）——
它不是骑墙，是**同族子集**。**遇到"两边都像"时，先考虑"它本来就是同一族的第三个"。**

### 4. 数字粘连是常态，不是例外

`356:SubmitPayment`、`140:SubmitShipping`、`150:GetStructureToken` —— 池子里相邻数字会粘。
**凡序号 > 200 一律复核；凡"步数"都不等于"序号差"。**

### 5. 一条线吃完要写"吃完"

流程序号这条线（R269–R277）最后落在：18 条流水线 / 141 步、2 条被证实为字面量、
14 条属未建模商店。**写清"到此为止 + 除非有新证据源"，比继续硬挖更有价值。**

## 九、守卫与证据（R296–R307 的六条硬教训）

### 1. **判方向 > 判存在**

同一个字符串，可能是"发出去的头"，也可能是"记在响应对象上的诊断"。
`X-Cyb-Transport` 看着像自己编的指纹头，实际写在响应的 `Headers[...]` 上，**根本不发**。
**先问"它往哪儿去"，再问"它在不在"。**

### 2. **"没有出处"有三种**

| 种 | 例子 | 处理 |
|---|---|---|
| 真发了、无出处 | `/v1/buys`、`/account/verify` | 代码行标 `inferred:` + 棘轮 |
| 只是写着、没发 | `/api/beast`（只在文档注释里） | 记为"待运行时复核" |
| 我没看懂它在哪 | `X-CSRF-TOKEN` 其实池里有小写 `x-xsrf-token` | 先复核自己的查法 |

### 3. **文案/名字差异 ≠ 功能差异**

`Settings.*` 有 238 个文案键，复刻件只引用了约六成 —— 但抽样三条（`BackupNow`、`ThreeDS`、`WindowMode`）
**全都有实现，只是标签是字面量**。这类计数**不能当缺陷探测器**，更不该进棘轮。
`Settings.Nav.*` 16 条里，**1 条是分组标题不是页面**（`ADVANCED`）—— 数量 ≠ 可导航项数。

### 4. **守卫自己会腐烂；新守卫必须立刻做变异检验**

- 锚点漂了 → 工具静默 skip，还在报告里算数（R284 修好 2 条哑护栏）；
- 断言比变异松 → "装饰性守卫"（R305 抓出我自己刚写的一条）。

### 5. **断言要落在"行"上，不是"文件"上**

`Assert.Contains(marker, 整个文件)` 会被同文件里**别的**标记行满足。
改成"**每个使用该名字的代码行都必须带标记**"后，一口气抓出 10 处漏标（R306）。

### 6. **变异要改"全部"，不是"一处"**

`replace(find, replace, 1)` 只改第一处，而第一处常在文档行（断言已忽略）→ 变异无效。
mutation-check 支持 `"all": true`；R307 用它才让两条新变异正常 fired。

### 7. 附：**先读守卫，再动手**

R300 我把 `ADVANCED` 加成第 16 个设置页，被几十轮前写的
`SettingsShellTests.AdvancedIsAGroupCaptionNotAPage` 拦下（连带红 4 条）。
**守卫记着的知识，往往正是我此刻缺的那一条。**

## §10 绑定缺口的口径有一个盲点（R342）

名字级口径（`tools/bind_diff.py`）问的是"整个仓库里有没有这个名字"，
所以**成员挂错类型也算满足**：

- `IWebhook` 应带 `Events` / `Type`，而复刻件的 `IWebhook` 只有 `ExtraFields` —— 但 `Events`、`Type`
  在 `TaskGroup` / 别处已有，**名字级口径看不见这个缺失**（缺口一直是 17，没动）。

新增 `tools/bind_scope.py`：按**类型自己的源码块**检查绑定成员，答案完全不同 ——
**23 个已存在类型**在各自类型上缺成员（`LoginControl` 缺 `Cancel/OpenBrowser/SignIn/SignUp/UseCode`、
`UserView` 缺 `OpenUrl`、`CreateModel` 缺 17 个……）。

### 使用纪律

- 它是**筛查器，不是判决**：块提取靠"下一个声明"启发式，**基类/partial 里的成员会被误报**；
- 每条都要**手工复核一次**再动手（R342 抽查 `LoginControl`、`UserView` 两条，均为真）；
- 修完一条就在 `docs/VERDICT.md` 记一行，别让这 23 条变成新的"一句话包着的 backlog"。


### §10.1 筛查工具本身也会骗人（R343）

`bind_scope.py` 的第一版用"下一个声明"做块边界，**同一份代码跑出 23 和 49 两个不同的数**。
改成**花括号配对 + 基类上溯**后稳定在 44，且已修好的类型（`LoginControl`）确实消失。

> 规则：**任何新指标都要先跑两遍、隔一轮再跑一遍**；两次不一致，先修工具，别修代码。


### §10.2 `bind_scope.py` 数的是类型，不是成员（R348）

两个类型各少 2 个成员，总数不动（41 → 41）。**看数时要同时看"类型数"和"成员数"**；
否则会把整轮的进展看成零。


### §11 没有版本控制时，禁止"按行号切文件"（R352）

这一轮我用"行号 + 下一个声明"的脚本删两个方法，**切掉了四个类**（`TaskDetailsView`、`GroupSummary`、
`TaskGroupListView`、以及 `TaskGroupView.Save/Reset`），现场无 git、无还原点。

救回来靠的是 `tools/.mutation-backup/`（变异测试工具的快照）。

**规则**：

1. 改结构一律**整段/整方法替换**，用前后锚点文本，不用行号；
2. 一次只切一处，**切完立刻编译**；
3. `tools/.mutation-backup/` 是唯一保险，**不要清空它**；
4. 如果非切不可，先手工把整文件复制成 `*.cs.bak` 再动手。


### §12 把纪律写成动作：写方法前先看一眼那个类的字段（R356）

"先读那一行"这条纪律，我这一程违反过至少五次（R259 猜 API、R302 猜模型、R325 猜依赖、R345 猜签名、
R356 猜字段），每次都是同一个后果：编译报错 → 回滚 → 重写。

**动作化**（比"记住"有效）：

1. 给某个类加成员之前，先 `grep 'class X' -Context 0,30` 看它的字段与构造签名；
2. 若该类型没有它需要的依赖（如 `ProxyGroupView` 没有 services/列表），**把依赖作为参数传进来**，
   而不是假设它存在；
3. 一次只加一个成员，**加完立刻编译**。


### §12.1 读类的时候，连基类一起读（R359）

`SolverWindow : Window` 我写了 `public new void Dispose() { … base.Dispose(); }`，
编译报 **`Window` 没有 `Dispose`** —— Avalonia 的 `Window` 不实现 `IDisposable`。

规则补一条：**加成员前，除了字段和构造，还要看一眼基类提供了什么**（有没有同名成员、是不是接口实现）。


### §12.2 读类时也要读"已有哪些方法"（R365）

`ProfileView` 我写了 `CurrentGroup()` 与 `ShowGroup(group)` —— 前者**重名**、后者**不存在**（叫 `Refresh`）。
字段读对了，方法没读。

规则：加成员前 `grep -E 'public|private' <file>` 看一眼**字段和方法**两张表；
`grep 'Config\.' <file>` 看一眼**配置里真实有哪些集合**（这一轮 `Config.Profiles` 就不存在）。


### §13 绑定成员可能要求"命令属性"的形状（R366）

池子里同一段字符串同时出现 `get_Add` / `get_Clear` / `get_Edit` / `get_Delete`，
说明原件里这些**绑定成员是返回 `ICommand` 的属性**，而复刻件写成了方法。
方法能表达同样的行为，但 **XAML 的 `Command=` 只能绑属性**。

现状：不重构（26 个视图全改代价大、无强制证据）；新增成员时，
**如果它明显是"用户动作"，优先写成 `ICommand` 属性**，与原件同形。


### §14 断言"注解"的测试保护不了"行为"（R385）

R384 我给备份文档加了 `System.Text.Json` 的 `JsonPropertyName`，而这个项目用 **Newtonsoft**，
属性完全被忽略 —— 文件照旧写错键名。而我当时写的测试**读的是注解本身**，于是绿灯。

规则：

1. 断言序列化结果，就**真的序列化一次再读键**（`JsonConvert.SerializeObject` + `JObject.Parse`）；
2. 加特性前先确认这个项目用的是哪个序列化器（`grep -r PropertyNamingPolicy|CamelCaseNamingStrategy`）；
3. 绿灯不等于正确：**测试要落在"用户能看到的东西"上**（文件内容、界面文本、返回值），不要落在中间表示上。


### §15 被测程序绝不能写进被参照程序的数据目录（R387）

复刻件的 `DataRoot` 原本就是 `%APPDATA%\Cybersole` —— 与原版完全重合。后果有两个，第二个更致命：

1. 会覆盖用户的真实配置（本轮已把原目录 16 个文件先留存）；
2. **"用实机文件核对模型"变成自我循环**：文件可能是复刻件刚写出来的，于是我"证明"了自己。

规则：

1. 复刻件一律写自己的目录（`%APPDATA%\CybersoleReplica`），并支持 `CYBERSOLE_DATA_ROOT` 覆盖；
2. 把参照数据当作**只读证据**（`AppPaths.OriginalDataRoot`，只读）；
3. 报告"实机一致"之前先问一句：**这份数据是谁写的？**


### §16 终端显示乱码 ≠ 文件乱码（R404）

这个控制台把 UTF-8 中文渲染成 GBK 乱码，**连没被改过的文件也一样**。
我在 R404 因此误判"账本乱码"，差点去修一个没坏的文件。

规则：判断编码只看字节 —— `io.open(p,'rb').read().decode('utf-8')`；终端输出只当渲染结果。
