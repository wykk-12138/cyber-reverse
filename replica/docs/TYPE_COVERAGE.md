# 类型级覆盖（生成物 —— 不要手改）

由 `python tools/type_coverage.py` 生成。完成判据 (a)：**类型级缺口、类型缺失 → 0**，
不可得写 Unknown + 缺什么。

**取证方式**：镜像的反射元数据里，属性形如 `<命名空间>.<类型>,<程序集>.<成员>!Getter`，
所以「原版某个类型有哪些属性」是一个**查询**而不是判断。复刻件侧读源码里的 `get` 访问器。

**范围**：下表只覆盖本工作一直在推理的核心类型。镜像有数千个类型，
而**本表不声称枚举了它们** —— 没列出的类型不因此而被判为缺席。

### `Cybersole.Core.CloudflareSolverConfig` ↔ `CloudflareSolverConfig`

**→ Unknown：原版侧查询为空（元数据命中 0）。**

**缺什么**：这个类型在镜像里的**真实名字**。`Cybersole.Core.CloudflareSolverConfig` 是本地猜的，而查询返回零 ⇒
两种可能：名字不对，或该类型的属性 getter 全被内联掉而不出现在这个形状里。
**→ 所以本行不计入缺口，也不计为已覆盖。**

## 二、结论

**类型级缺口合计：0**（只计原版侧**查询成功**的类型）。

**而 1 个类型的原版侧查询为空 ⇒ 记为 Unknown，不计入缺口：** `CloudflareSolverConfig`

**→ 在**查询成功**的类型上，(a) 的缺口为 0**：镜像的每个属性在复刻件里都能找到。
→ 而「复刻件自加」的几个字段各有理由（本地主键、以及用列表成员表达镜像的 `EnabledProviders` 集合），
那些是**表示选择**，不是缺口 —— 而把理由写在表里，是为了让它们不变成下一轮的假缺口。

## 三、边界

- **只比属性名，不比类型**：镜像的元数据里没有属性的 CLR 类型，所以 `Balance` 是 `double` 还是 `string` 本表不问。
- **只比属性，不比行为**：属性齐了不等于行为等 —— 那要到方法级，而 R1045 说产物无符号，方法级要另找路径。
- **元数据可能不全**：若某属性的 getter 被内联掉，它可能不出现在这个形状里，
  那样「镜像属性数」就是**下界**而不是全量。
